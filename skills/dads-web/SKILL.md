# DADS による Web UI 設計・実装

DADS（[デジタル庁デザインシステムβ版](https://design.digital.go.jp/dads/)）は、行政・公共向けを想定した **プラットフォーム型** のデザインシステムだ。単一ブランドの見た目を強制するものではなく、アクセシビリティと情報設計の枠組みを提供する。このスキルではその枠組みを Web UI の設計・実装に使う。

同梱の Markdown アーカイブ（`references/dads-markdown/`、2026-09-09 版）を正本として読む。サイト全体を一度に読み込まない。必要なページだけ開く。

## いつ使うか / 使わないか

**使う**

- 新規の Web / アプリ画面を DADS の原則で設計・実装する
- 既存画面を DADS の foundations（色・文字・余白・コントラスト）やコンポーネント規約に寄せる
- 「公共向け」「読みやすさ優先」「色だけで状態を伝えない」を明示された UI 作業

**使わない（他スキルへ）**

| 依頼 | 使うスキル |
| --- | --- |
| PowerPoint / スライド | `dads-powerpoint` |
| 表 vs カード等の汎用情報設計レビュー | `screen-design-review` |
| 商用スタイル・パレット・フォント探索 | `ui-ux-pro-max` |
| プロダクト固有の admin UI 契約が既にある画面 | その契約（例: `docs/admin-ui.md`）を正。DADS は差分の根拠参照のみ |

全面を DADS 見た目に置き換える前に、プロダクトの目的を確認する。高密度の業務コンソールでは、DADS 自身も行間を詰めてよいと書いている。文字サイズ下限など **転用できる原則** と、公開サイト向けの余白・Display 見出しなど **捨てるべき見た目** を分ける。

## 作業の進め方

1. **成果物の性質を決める。** 公開サイト / 手続きフォーム / 業務コンソール / コンポーネント単体。密度と行間の前提が変わる。
2. **既存のスタイルガイドや UI 契約があれば先に読む。** 衝突する指定はユーザー確認か、契約側を優先する。
3. **foundations から読む。** いきなりコンポーネント HTML を真似ない。色・文字・余白・コントラストが先。読み順は [read-map.md](references/read-map.md)。
4. **必要なコンポーネント文書だけ開く。** ボタン、フォーム、チップラベル、通知バナー、テーブルなど、使うものに限定する。
5. **スタイルガイドとして適用する。** キーカラーはプロダクトのブランドに合わせてよい。プライマリは背景とのコントラスト 4.5:1 以上。状態は色だけでなくテキストで示す。
6. **実装する。** 既存スタック（React / Tailwind / shadcn 等）に載せる。DADS の React/HTML サンプルや `@digital-go-jp/tailwind-theme-plugin` は任意の参照実装であり、既存トークン体系を壊してまで全面置換しない。
7. **納品前に確認する。** 文字サイズが意図せず 14px 未満になっていないか（業務 UI で 12px まで詰めるならその判断を明示）、状態のテキスト併記、フォーカス可視、出典表記。

## 設計上の要点（なぜ重要か）

- **アクセシビリティが先。** DADS の中心価値。コントラストと「色だけに依存しない」状態表示を落とすと、見た目を寄せても意味がない。
- **タイポの下限を意識する。** 本文・UI はおおむね 16px 以上が基準。14px は領域制約時のみ。14px 未満は原則不可。業務コンソールで情報量を優先して 12px まで下げるなら、その例外をプロダクト契約に書き、さらに小さくしない。
- **行間は用途で変える。** 読み物は 1.5 以上。管理画面・一覧は 1.2〜1.3 まで詰めてよい、と DADS 自身が書いている。
- **コンポーネントは意味で選ぶ。** チップラベルは状態・分類、チップタグはユーザーが付けた値。通知バナーと緊急時バナーを混同しない。
- **公式ロゴや「準拠証明」を勝手に付けない。** 出典は「デジタル庁デザインシステムの資料をもとに編集・加工」と公式 URL。公認表示はしない。
