# Visual specification

The view helps a returning developer decide, not merely read. Present structure and status before prose.

## Information architecture

Use a sidebar plus main dashboard with these fixed panels:

| ID | Question |
|---|---|
| `resume` | What should I do now? |
| `intent` | Why does this project exist? |
| `people` | Who owns or understands it? |
| `design` | How is it shaped? |
| `ops` | How does it run? |
| `gaps` | What is missing or risky? |
| `grow` | How can this report be extended? Generated by the script, not the model. |

Keep empty panels and explain why no content applies. This distinguishes absence from omission.

## Semantic design

- Green: healthy or resolved
- Amber: attention, WIP, or human dependency
- Red: danger or required action
- Blue: next action, emphasis, or link

Use color only for meaning. Keep parallel cards on the same surface level. Reserve inset wells for code. Limit summary tiles to six and next actions to three.

## Surface and interaction

- Dark navy/charcoal dashboard with readable Japanese text and AA contrast.
- Large but consistent card radii, restrained shadows, and clear surface steps.
- Sidebar stays visible on desktop and becomes an accessible drawer on narrow screens.
- Preserve hash routing, keyboard navigation, reduced-motion behavior, printable light styling, and a readable no-JavaScript linear fallback.
- Self-contained vanilla HTML/CSS/JS only; no CDN, external font, React, or Tailwind dependency.

The template and `build-overview-html.py` are the implementation source of truth. Do not duplicate their HTML fragments in instructions.
